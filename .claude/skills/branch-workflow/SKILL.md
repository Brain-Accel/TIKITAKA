# 브랜치 작업 흐름

작업을 시작하기 전에 테스트인지 실기능인지 정합니다. 둘은 브랜치를 따는 곳과 끝맺는 방식이 다릅니다.

| 구분 | 판단 기준 | 브랜치 | 끝맺기 |
|---|---|---|---|
| 테스트 | 요청에 "테스트로", "테스트용" 같은 말이 있음 | 현재 브랜치(보통 main)에서 `test/<주제>` | 결과물을 이 브랜치에 합침. PR 없음 |
| 실기능 | 테스트라는 말이 없음 | `dev`에서 `<type>/<이슈번호>-<주제>` | 푸시하고 `dev`로 PR. 병합은 사람이 함 |

어느 쪽인지 헷갈리면 시작하기 전에 한 번 묻습니다.

## 테스트 작업

1. 현재 브랜치에서 `test/<주제>` 브랜치를 만듭니다.
2. 워크트리를 쓰면 이 브랜치에서 땁니다: `git worktree add <경로> -b <임시 브랜치> test/<주제>`.
3. 작업이 끝나면 결과를 `test/<주제>`에 fast-forward로 합치고, 워크트리와 임시 브랜치를 지웁니다. 합치는 일을 사용자에게 넘기지 않습니다.
4. 합친 상태에서 검증을 다시 돌립니다. backend는 `./gradlew test`, app은 `tsc`와 ESLint입니다.
5. 푸시하지 않고 PR도 열지 않습니다.

## 실기능 작업

1. 연결할 Issue가 없으면 만듭니다. 모든 작업은 Issue에서 시작합니다(CLAUDE.md).
2. 최신 `origin/dev`에서 `<type>/<이슈번호>-<주제>` 브랜치를 땁니다. type은 커밋 type과 같습니다: `feat`, `fix`, `refactor`, `docs`, `chore`.
3. 워크트리를 쓰면 결과를 이 기능 브랜치에 합치고 워크트리를 지웁니다.
4. 검증이 통과하면 묻지 않고 푸시한 뒤 `gh pr create --base dev`로 PR을 엽니다. 본문에 `Closes #<이슈번호>`를 넣습니다.
5. 병합하지 않습니다. 상대방이 승인한 뒤 사람이 병합합니다.
6. 아직 병합되지 않은 PR 위에 쌓아야 하면 그 PR의 브랜치에서 따고, 새 PR의 base를 그 브랜치로 둡니다.

## 하지 않는 것

- main이나 dev에 직접 커밋하거나 force-push하기
- `dev`가 없을 때 임의로 만들기. 없으면 사용자에게 묻습니다.

## pstack과 함께 쓰기

pstack Feature 플레이북의 서브에이전트 위임과 워크트리 분리는 그대로 씁니다. 끝맺는 방식만 이 문서를 따릅니다.

- Claude Code의 `isolation: "worktree"`는 원격 기본 브랜치(main)에서 땁니다. 위 표의 브랜치를 먼저 만들고, 그 브랜치에서 `git worktree add`로 직접 땁니다.
- 테스트 작업에서는 "Opening a PR" 단계를 `skip: 테스트 브랜치, PR 없음`으로 남기고, 대신 위의 합치기와 재검증을 합니다.
- 실기능 작업의 PR base는 main이 아니라 `dev`입니다.
